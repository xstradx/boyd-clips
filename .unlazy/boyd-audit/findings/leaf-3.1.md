# leaf-3.1 — silent failure hunt

Territory: every place this codebase turns a failure into a quietly worse output.
Every line number below was read from the working tree on 2026-08-29 and every
disk claim was measured with a command, not inferred. Read-only: no repo file was
modified and no pipeline script was executed.

**The thesis is confirmed, and the mechanism is worse than CLAUDE.md states.**
CLAUDE.md says the six elements "silently degraded to 'off' ... because the code
accepted a missing asset and logged a line instead of failing". That is true and
there are nineteen instances below. But the log line is only half of it. The other
half is that **nothing on any render path measures the finished file**, and
**nothing a human reads afterwards records which of the six were applied.**
`manifest.json` (pipeline.py:872-876) stores path, title and duration; `REVIEW.txt`
(pipeline.py:884-917) prints duration and title. So the warning is not a weak
signal, it is the *only* signal, it scrolls past at 19:40 under Task Scheduler
(run_daily.ps1:38), and by the time a human opens the folder nothing distinguishes
a correct render from one missing its intro, watermark, captions and thumbnail.
That is why these survived multiple releases, and it is why the highest-value fix
in this audit is a bookkeeping change rather than a render change.

**The single highest-blast-radius fix: F1.** Not because it is the worst bug —
F2, F3 and F4 are worse — but because it is the one change that makes every other
bug on this list self-reporting. Nathan's stated goal is reliability, and the
reliability failure here is not that things break; it is that things break
invisibly while the process reports success. F1 costs about thirty lines, changes
no render decision, and after it lands the rest become visible defects fixable in
priority order instead of rediscovered one shipped video at a time. Do it *first*,
before any fail-closed change, so the scale of the existing damage is known. Pair
it with F3 (stage the file, promote to READY-TO-POST only on a pass) and the two
together close the human-facing half of the problem.

CONTRAST — what `scripts/make_short_auto.py` does right, and its two holes. The
pattern: run the chain, then **probe the finished artefact** — not the log, not
the config — against five independent boolean checks (:180-188), accumulate with
`ok &= bool(good)`, print a PASS/FAIL table, and return a distinct non-zero exit
code (4) meaning "produced but refused". The checks are well chosen and each
encodes a bug that actually shipped: `pix_fmt yuv420p` (four shorts shipped High
4:4:4 that no consumer decoder plays, :32-33), exact `1080x1920`, A/V duration
agreement within 0.15s, no residual word gap, and a full `-f null -` decode pass.
Crucially they measure the OUTPUT FILE, which is exactly the lesson
verify_render.py:12 states: "Logs describe what the code attempted. They cannot
describe what came out."

**This pattern is liftable into the rest of the codebase, and most of the inputs
already exist.** `render_longform` and `render_short` already call
`probe_duration(out_path)` (render.py:1382, :1574) — a probe of the finished file
is already happening, it just asks one question instead of six. What it would take:
(a) a `gates.py` holding one predicate per element, each measurable from the output
file plus values already in scope — intro present (`lf_duration - planned_s` within
0.2s of `probe_duration(intro)`), watermark present (assert the overlay filter was
emitted and its input indexed, or measure the mark's corner region), captions
present (`len(events)`, already computed at render.py:1120), grade applied (the
`cfg.get("color", {}).get("enabled", True)` branch at render.py:1520), dead air
removed (`raw_s - kept_s`, already computed at pipeline.py:311), thumbnail written
(file exists, non-trivial, and which builder ran); (b) calling it *before*
`save_clip`, not after; (c) writing the result into the manifest (F1).

**Two things must change for the lift to work, and they are precisely the two holes
make_short_auto still has.** First, **a gate must not pass on empty input** — F11
shows its dead-air check returns PASS on an empty word list, and its A/V-sync check
passes on a file where both probes returned `""` (`float("" or 0)` = 0.0 for both,
so `abs(0-0) < 0.15`). Second, **a failed gate must move or refuse to write the
file, not merely return an exit code** (F3). Lifted with those two corrected, this
one pattern subsumes F4 through F9 and F14. Without them, it would spread a
verification that says PASS on exactly the failures it was built to catch.

## F1: neither manifest.json nor REVIEW.txt records whether any of the six elements was applied, which is what makes every other finding in this audit invisible
SEVERITY: high
EVIDENCE: C:\Users\natha\Projects\boyd-clips\src\boydclips\pipeline.py:872-876 — the manifest's entire record of what was produced is `"outputs": {k: {kk: vv for kk, vv in v.items() if kk != "description"} for k, v in result.items() if k in ("longform", "short") and v}`, and `result` is populated at :412-424 and :531-537 with only `clip_id`, `file_path`, `title`, `description`, `duration_s`. The human-facing summary is no better: :884-905 emits `f"  file:  longform.mp4  ({lf['duration_s']:.0f}s)"` and the same for the short, plus titles. `state.py:308-311` records `INSERT OR REPLACE INTO clips (... file_path, duration_s, title, description, rendered_at, status, spec_version) VALUES (?,?,?,?,?,?,?,?,'rendered',?)` — a status literal, never a measurement. WHY-IT-MATTERS: This is the mechanism behind CLAUDE.md's complaint, not merely an instance of it. F2 through F19 each disable one of the six, and they are all survivable as shipped bugs only because the folder a human opens contains no evidence anything was missing. `run_daily.ps1:34-40` gates on `$LASTEXITCODE`, which is 0 for every degradation in this document. Make `_watermark_chain` and `build_ass` return what they did rather than only their filter string, so the flags are measurements rather than restatements of intent. Print any element that is off with an unmissable marker.
COST: Moderate — perhaps half a day, because it touches the return signatures of `_watermark_chain` (render.py:1220) and `build_ass` (render.py:917) and both renderers. Risk to behaviour is near zero: purely additive, changes no render decision, old manifests simply lack the key. The real cost is that it will immediately expose how many renders already in `out/review/` are missing elements — which is the point, and the reason to land it before any fail-closed change.
