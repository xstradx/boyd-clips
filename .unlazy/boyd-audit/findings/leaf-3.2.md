# leaf-3.2 — verification and test coverage

Read-only audit. Nothing in the repo was edited, created, moved or deleted except
this file. The pytest suite was run from the scratchpad (not the repo root)
because `tests/test_pipeline.py:362` writes `_overlap.ass` into the CWD — see F13.

### Headline

The pipeline has a lot of verification code and almost no *proven* verification.
97 tests pass in 2.85s and not one of them looks at a rendered pixel or a muxed
file. Of the checkers that do measure artifacts, the two that were calibrated
against a positive and a negative control (`verify_render.py`, `verify_set.type_mask`)
are genuinely good; the rest were written, never tested against a known answer,
and three of them demonstrably do not do what their name says. Nothing runs
automatically at any point.

### Proposed gate set

One gate per mandatory element, each keyed on a signature only the target has,
each with a named positive and negative control, each exiting non-zero. I
validated the first three during this audit; the rest are specified but not yet
validated and are labelled so.

**G-CAPTION (element 5) — VALIDATED IN THIS AUDIT.** Signature: the caption glyph
mask from `verify_set.type_mask` (`L>238` with an `L<45` pixel within 17px)
counted separately in the top and bottom half of the 1080x1920 frame, sampled
every 2s. Measured controls: positive `CARTHIEF_SHORT_FINAL.mp4` = 12,914 /
20,422 / 21,650 / 22,322 / 20,313 / 38,207 px in whichever half holds the
caption; negative `CARTHIEF_SHORT.mp4` (same footage, uncaptioned) = max 2,878 px
in any half. Threshold 6,000 sits in a 4.5x gap with room both sides. The same
measurement gates *side* as well as presence: at t=30s the count flips to
38,207 bottom / 64 top, which is the speaker-side switch. PASS = every sampled
frame has exactly one half over 6,000, and the over-6,000 half agrees with
`speakers.json` for that timestamp.

**G-LIMB (element 6) — replaces the broken one.** Signature: silhouette area loss
against the untouched source plate, which is already written and correct in
`verify_thumbnail.silhouette_loss` at a 1% threshold. It just needs a `--plate`
CLI flag instead of the undocumented env var (F2). Controls: negative
`CARTHIEF_thumbnail.jpg` (STATE.md:177-181 records the severed arm), positive
`1_LONGFORM_thumbnail.jpg`. Delete `verify_set`'s column-jump metric — F1 shows
it separates the two controls by 4.7% vs 3.6%, which is noise.

**G-DEADAIR (element 2) — measure the render, not the plan.** Signature:
`render.detect_silences` on the *rendered output file's* audio at the
CONTENT_SPEC threshold. I measured this works: `CARTHIEF_SHORT.mp4` at -30dB /
min_silence 4.0s returns **0 spans** (a clean positive control), while the same
file at min_silence 0.70s returns 16 spans totalling 25.6s. So the detector is
not blind; run it on `a.out` and fail on any span over the config threshold.
Negative control: the untightened `CARTHIEF_SHORT.mp4` at the 0.70s scale.

**G-FRAMING — already exists, just wire it up.** `verify_render.py` is correct
and its threshold is swept over a 24-render distribution. Nothing calls it. Add
it to `run_case.py` after each render.

**G-STING (element 3) — specified, NOT yet validated.** Signature: extract the
frame at t=0.7s of the output and correlate it against the same frame of
`boyd-brand/sting_v2.mp4`; the sting is a synthetic dark ground with the TTT
star, so normalised cross-correlation should be near 1.0 against the asset and
near 0 against any courtroom frame. Positive control:
`READY-TO-POST/1_LONGFORM_Thompson.mp4`, which STATE.md:196-198 records as
carrying the 1.4s sting and already verified by exactly this frame extraction.
Negative control: `CARTHIEF_LONGFORM.mp4` body, or any raw `work/` section.

**G-WATERMARK (element 4) — specified, NOT yet validated.** Do not key on
brightness: I tested the glyph signature and the persistent ~1,600-3,300px floor
in these frames is scattered background detail (bbox x 507-851 / x 18-1652), not
the mark. The right signature is *temporal invariance at a fixed ROI*: the
watermark is an alpha-composited PNG at a constant position
(`assemble_final.py:24-25`, top-right, `W-w-34 : 34`, width `0.06*1920` = 115px),
so per-pixel variance across N sampled frames inside that ROI is near zero while
the surrounding background moves. PASS = ROI variance below the frame's median
block variance by a large margin. Positive control: any render built while the
logo path resolved. Negative control: the first 2.6s (the intro), where
CLAUDE.md:51 says the watermark must *not* be. This gate would have caught F3 on
its first run.

**G-GRADE (element 6) — specified, uses an existing validated metric.** Use
`verify_Q3_detail.chroma_flat_dev` (local chroma deviation), not either of the
absolute-deviation implementations. Its docstring records it separating cleanly
where the others do not: shipped Thompson 0.73, CARTHIEF 1.30, SANCHEZ 1.41,
OFFERUP 1.35, against absolute deviation reading 33.0 and 89.9 on the same
files. Pair with the existing luma window. Controls: Thompson (positive), the
147.1 and 155.9 builds Nathan rejected as "really brifht" (negative).

**Wiring.** All of the above belong in `run_case.py` after each artifact is
produced, gating the move into `READY-TO-POST` rather than running after the
file is already there (F10), plus `pytest` in a pre-commit hook. Every one
exits non-zero on failure — F11 shows two current checkers do not.

## F1: `verify_set.py`'s LIMB check — the entire content of gate G5, "No severed limb" — passes the file STATE.md records as still shipping a severed arm, and separates the known-bad from the known-good by less than the noise between them.

SEVERITY: blocker
EVIDENCE: Ran `verify_set.check()` directly on both controls (no files created). Known-bad `READY-TO-POST/CARTHIEF_thumbnail.jpg`, which STATE.md:177-181 records under "What is NOT fixed" as *"the shipped CARTHIEF_thumbnail.jpg is still wrong"* with a severed arm from `regroup_plate.py`, returned: `note: CARTHIEF_thumbnail.jpg silhouette edge jump 32/676` and **no LIMB failure** (its only 2 failures were LUMA and ARROW). Known-good `1_LONGFORM_thumbnail.jpg` (the shipped, posted Thompson) returned `silhouette edge jump 26/715` and 0 failures. The gate at `scripts/verify_set.py:172` is `if span and worst > 0.55 * span:` — for CARTHIEF that requires `worst > 371`, and the measured value is `32`, off by a factor of 11.6. The metric is `col_counts = m.sum(axis=0)` (verify_set.py:164), the *count* of silhouette pixels per column; a forearm severed by a vertical rectangle edge removes only the limb's own height from that column (~30-60px), never 55% of the body's height. Bad 4.7% vs good 3.6% — the two controls are indistinguishable.
WHY-IT-MATTERS: GATES.md G5 is stated as `EXPECT: LIMB: 0 failures`, and `0.55 * span` guarantees that expectation is met on every thumbnail this pipeline can produce short of cutting a body in half. The one defect Nathan has called out by name — "theres have to be surgical cuts not slop" — is gated by a check that cannot fire. Once G5 is ticked, a severed-limb thumbnail ships with an automated PASS behind it, which is worse than no check at all because it displaces the human look.
PROPOSAL: Delete the column-jump metric. Replace with the area-loss comparison already written correctly in `verify_thumbnail.silhouette_loss` — `(plate_person_area - final_person_area) / plate_person_area > 0.010` — which is the same 1% rule STATE.md:96-97 says the Q3 builder already enforces internally ("over 1% and the move is REJECTED"). Signature: silhouette area against the untouched source plate, which only a cut subject loses. Controls: negative `CARTHIEF_thumbnail.jpg` + its plate, positive `1_LONGFORM_thumbnail.jpg` + its plate. Assert in a test that the checker FAILS the negative before trusting any PASS.
COST: Low effort — ~20 lines, the measurement already exists in the sibling file. Risk low and read-only to fix. The real cost is that G5 must be un-ticked in GATES.md and the Q3SET re-checked.

## F2: `verify_thumbnail.py`'s SILHOUETTE_CUT check — the only check in the repo written specifically for the severed-limb defect — is a silent no-op that no invocation can ever enable.

SEVERITY: blocker
EVIDENCE: `scripts/verify_thumbnail.py:483-489` sets `m["limb_loss"] = None`, then `sp = os.environ.get("THUMB_SOURCE_PLATE")` and only calls `silhouette_loss` `if sp:`. The consumer at line 533 is `if m.get("limb_loss") is not None and m["limb_loss"] > THRESH["limb_loss_frac"]`, so with no env var the check is skipped in silence — no warning, no note, no line of output. The CLI cannot supply it: `main()` at lines 551-553 defines exactly two arguments, `paths` (nargs="+") and `--calibrate`. There is no `--plate`. `grep -rn 'silhouette_loss\|source_plate\|THUMB_SOURCE_PLATE' .` across the whole repo returns only the definition site and one prose mention in `verify_Q3_detail.py:53` — **nothing anywhere sets that variable**. The env var is also undocumented: the module docstring (lines 9-15) lists five checks and does not mention limb loss at all. Confirmed the check never fires: running `python scripts/verify_thumbnail.py <Thompson> <CARTHIEF>` printed 4 failure lines across the two files, none of them SILHOUETTE_CUT.
WHY-IT-MATTERS: The function's own docstring (lines 404-411) says it exists because a severed arm "is exactly what shipped, and what the previous verification missed". The fix for that incident was written, wired to a variable nobody sets, and has therefore never run once. Combined with F1 — where the *other* limb checker fails its control — the repo has two limb checks and zero working ones, while GATES.md carries G5 as a gate that will read as met.
PROPOSAL: Add `--plate PATH` to the argparse block and pass it through `measure()`; keep the env var as a fallback. Then make the no-op impossible to reintroduce: when `limb_loss is None` emit an explicit `~ LIMB_NOT_CHECKED (no --plate given)` warning line, so an unrun check is visible rather than absent. Signature stays the 1% area loss. Controls: assert FAIL on `CARTHIEF_thumbnail.jpg` + plate and PASS on `1_LONGFORM_thumbnail.jpg` + plate, as a pytest case so it cannot silently regress.
COST: Very low effort, ~10 lines. Risk: none to existing behaviour. Needs the source plates to be locatable — `make_thumbnail_auto.py --auto-plate` chooses them, so the path should be recorded in the `.meta.json` sidecar that already exists next to `Q3_detail.jpg`.

## F3: The watermark — mandatory element 4 — has no checker anywhere, and both code paths that draw it are designed to degrade silently to "no watermark"; one of them is currently pointing at a path that does not exist.

SEVERITY: high
EVIDENCE: No checker measures element 4. `grep -rln 'watermark\|wm_' scripts/*.py` returns builders (`make_watermarks.py`, `make_watermarks_v2.py`, `assemble_final.py`, `rebuild_longform.py`) plus `verify_render.py`, which mentions the watermark only in its prose docstring about a past incident ("the watermark was burned in twice") and never measures it. Both drawing paths log-and-continue rather than fail. **Live pipeline:** `src/boydclips/render.py:1247-1249` is `if not path.is_file(): log.warning("watermark not found, rendering without it: %s", path); return [], f"[{in_label}]null[{out_label}]"` — a null filter, render proceeds. Its docstring at 1240-1241 states this as deliberate: *"a missing asset degrades to 'no watermark' rather than failing a render that is otherwise fine."* This path currently resolves — `DEFAULT_WATERMARK` is a candidates list and I confirmed the first entry exists: `EXISTS: /c/Users/natha/OneDrive/Desktop/Boyd Clips/boyd-brand/watermarks_v2/wm_brand_halo_40.png` (line 1211), with the shallow variant at line 1212 `MISSING` as intended fallback. **Script path:** `scripts/assemble_final.py:20` is a single hardcoded `LOGO = Path(r"C:\Users\natha\OneDrive\Desktop\boyd-brand\logo_transparent.png")` with no candidates list, and I measured it does not resolve: `MISSING: /c/Users/natha/OneDrive/Desktop/boyd-brand/logo_transparent.png` while `EXISTS: /c/Users/natha/OneDrive/Desktop/Boyd Clips/boyd-brand/logo_transparent.png` — one directory too shallow. Lines 145-150 then take the else branch: `print(f"NO LOGO at {LOGO} - shipping unwatermarked, flagged"); marked = joined`. That is the same breakage `render.py:1180`'s comment says was already fixed once in the live path — *"the old absolute path stopped resolving"* — reintroduced in the script and never noticed, because nothing checks.
WHY-IT-MATTERS: The degradation is the mechanism CLAUDE.md:58-61 was written to stop — *"Every one of these has silently degraded to 'off' at some point because the code accepted a missing asset and logged a line instead of failing. If a render finishes and any of the six is absent, that is a bug, not a preference."* `render.py:1240` states the opposite policy in its docstring, so the code and the project rule are in direct conflict, and no gate arbitrates. "flagged" in `assemble_final.py` is aspirational: nothing consumes the flag and the exit code is unaffected. The live path happens to resolve today, which is exactly the problem — that is a fact about the current disk, established by me in this audit and by nothing in the pipeline, and it silently stopped being true once already. With no checker, the only thing between an unbranded upload and the channel is Nathan noticing.
PROPOSAL: (a) Give `assemble_final.py` the same candidates list `render.py:1211-1212` uses, and make a missing mandatory asset raise rather than branch in both — the six elements should fail the render, per CLAUDE.md, not degrade. (b) Add G-WATERMARK keyed on temporal invariance at the fixed ROI, since the mark is composited at a constant position (`assemble_final.py:24-25` top-right `W-w-34 : 34`, width `0.06*1920`=115px; `render.py:1251-1252` uses `watermark_width_frac` / `watermark_margin_frac` 0.035): sample N frames from the body and require per-pixel variance inside that ROI to be near zero while the frame's median block variance is not. Positive control: any current long-form built through `render.py`, where the asset resolves. Negative control: the first 2.6s (the intro), where CLAUDE.md:51 says the watermark must be absent — that control also proves the gate can fail. Note this gate is specified, not yet validated.
COST: Path/candidates fix is a few lines, zero risk. The gate is medium effort (~40 lines plus control frames) and must be shown to FAIL its negative control before being trusted, per F1.

## F4: `verify_thumbnail.py` FAILS the shipped, posted Thompson reference on two of its own checks, which by the file's own stated rule means two thresholds are wrong — and it has been left in that state.

SEVERITY: high
EVIDENCE: Ran `python scripts/verify_thumbnail.py "…/READY-TO-POST/1_LONGFORM_thumbnail.jpg" "…/READY-TO-POST/CARTHIEF_thumbnail.jpg"`, exit code 1. Output: `FAIL 1_LONGFORM_thumbnail.jpg` / `- ARROW_AIMS_AT_NOTHING the ray from the tip reaches no face - it points at empty background` / `- CHROMA_BLOCKING flat bright area deviates 3.7 from neutral (clean is ~1.3)`, then `FAIL CARTHIEF_thumbnail.jpg` with ARROW_ON_PERSON 2% and CHROMA_BLOCKING 89.9, ending `0/2 passed`. The file's own docstring at lines 4-7 states the governing rule: *"Every threshold in THRESH was measured against the 12 competitor thumbnails… The rule is: the competitor set is ground truth. If a check fails a competitor, the threshold is wrong."* Thompson is stronger than a competitor — STATE.md:193-196 records it as the one package actually posted from this pipeline. STATE.md:186-188 already names this defect and it remains open. Note the arrow threshold is inconsistent with its sibling: `verify_set.py` passes Thompson's arrow cleanly (`arrow 3904px`, 0 failures), so the two files disagree about the same image.
WHY-IT-MATTERS: A verifier that fails its own ground truth is unusable in either direction. Nobody can wire it into `run_case.py` because it would block every render, and nobody can trust a PASS from it because two of its twelve checks are known-miscalibrated and it is not recorded which of the remaining ten were ever exercised. In practice it means the thumbnail stage — the element with the most checker code in the repo — has no runnable gate, and `verify_set.py` inherited the job without inheriting the calibration discipline.
PROPOSAL: Fix the two thresholds against the control rather than deleting the checks, since both defects they target are real. ARROW_AIM: the `arrow_aim_miss_frac=0.16` ray search (lines 388-398) casts from the tip along the centroid→tip axis and requires a *Haar face box* hit; Thompson's arrow points at a body, not a face. Change the target from face boxes to the rembg person mask — which is exactly what `verify_set.py:126-142` does and why it passes Thompson — and re-derive the threshold. CHROMA: replace `flat_chroma` with `verify_Q3_detail.chroma_flat_dev` per F5. Then add a standing regression test: `verify_thumbnail.py` must PASS `1_LONGFORM_thumbnail.jpg` and FAIL `CARTHIEF_thumbnail.jpg`, asserted in pytest so a future threshold change cannot silently re-break the control.
COST: Medium effort — two thresholds to re-derive against the 12-thumbnail competitor set plus Thompson, both re-derivations already have the measurement code written. Low risk. High value: it converts the repo's most complete checker from unusable to wired.

## F5: Three implementations of the same "flat chroma" metric disagree by up to 43x on the same file, and the two in active use are the two the third documents as wrong.

SEVERITY: high
EVIDENCE: On the identical file `READY-TO-POST/CARTHIEF_thumbnail.jpg`: `verify_set.flat_chroma` (scripts/verify_set.py:55-72) returned `chroma 2.11` — a PASS against its `CHROMA_MAX = 6.5`. `verify_thumbnail.flat_chroma` (scripts/verify_thumbnail.py:422+) returned `89.9` — a FAIL against its `flat_chroma_dev=3.5`, printed as `CHROMA_BLOCKING flat bright area deviates 89.9 from neutral`. Same image, same nominal metric, 43x apart, opposite verdicts. The third implementation, `verify_Q3_detail.chroma_flat_dev`, diagnoses both in its docstring (scripts/verify_Q3_detail.py:46-61): *"Absolute distance from neutral is the wrong measure and I had it wrong first: it counts real colour, so on the flattest quarter of a frame containing a county-orange jumpsuit it reads 15.9 on this build and 33.0 on the shipped CARTHIEF… verify_thumbnail.flat_chroma has the same failure in a sharper form — it takes the BRIGHTEST flat 100x100 patch, which on the shipped CARTHIEF lands on the jumpsuit and returns 89.9 against Thompson's 3.7 on a neutral ceiling."* It then records the local form separating cleanly: Thompson 0.73, CARTHIEF 1.30, SANCHEZ 1.41, OFFERUP 1.35.
WHY-IT-MATTERS: The correct metric was identified, written down and measured — and then left in a one-off bake-off script while both broken versions stayed in the two checkers that GATES.md G8 and the thumbnail gate actually call. `verify_set`'s version happens to return a passing 2.11 on CARTHIEF for the same jumpsuit reason, so G8 (`CHROMA: 0 failures`) will read as met by luck rather than by measurement, and `verify_thumbnail`'s version fails Thompson (F4). This is the exact shape of Nathan's recorded lesson: the verification was wrong, not the render, in both directions at once.
PROPOSAL: Promote `chroma_flat_dev` into a shared module and delete both absolute-deviation copies. Signature: chroma minus its own *local* mean inside the flattest luma quartile — a signature only block-to-block chroma variation has, which real colour does not. Controls are already measured and recorded in the docstring: positive Thompson 0.73, negative the Q2_surgical build at 14.96 that STATE.md:88 says was disqualified on chroma. Set the threshold in the gap between 1.41 (worst passing) and Q2's value, and assert both controls in pytest.
COST: Low-medium — the working implementation exists and is measured; the work is moving it, deleting two copies, and re-deriving one threshold. Risk: G8's current "met" status is invalidated and the Q3SET needs re-checking.

## F6: Nothing runs any verification automatically. There is no CI, no git hook, no pytest configuration, and `run_daily.ps1` — the scheduled task that drives the whole pipeline — never invokes a single checker.

SEVERITY: blocker
EVIDENCE: `ls .github` → `ls: cannot access '.github': No such file or directory`. `ls .pre-commit-config.yaml` → `No such file or directory`. `ls .git/hooks` → only the ten `*.sample` files git ships, none installed. `cat pyproject.toml` contains no `[tool.pytest.ini_options]` section — no `testpaths`, no `addopts`, so even `pytest` from the root is unconfigured. `cat run_daily.ps1` shows the entire scheduled body: `python -m pip install --quiet --upgrade yt-dlp`, then `python -m boydclips.cli doctor`, then `python -m boydclips.cli run` — nothing else. `grep -rn 'verify_render\|verify_set\|verify_thumbnail\|check_vertical\|audit_cuts\|make_short_auto' src/ scripts/run_case.py run_daily.ps1` returns exactly one hit in the entire pipeline: `scripts/run_case.py:109: ok = run([PY, str(ROOT / "scripts" / "make_short_auto.py"),`. No `verify_*` script is called by any code path.
WHY-IT-MATTERS: Every checker in the inventory table only ever runs when a human types it, which means in practice they run once when written and never again. That is why F1, F2, F4 and F5 could all be true simultaneously without surfacing: nothing re-runs them, so nothing reports that they drifted or never worked. It also means the 97 passing tests protect nothing during the 19:40 unattended run — the exact scenario `tests/test_pipeline.py`'s own docstring says it was written for ("silent ones that only surface at 3am inside a scheduled run"). A pipeline whose stated goal is autonomous daily posting currently has zero automated quality gates between the source stream and `READY-TO-POST`.
PROPOSAL: Three wirings, cheapest first. (a) A `.git/hooks/pre-commit` running `pytest tests/test_pipeline.py -q` — 2.85s, no excuse not to. (b) `run_case.py` calls `verify_render.py` after each render and the F1/F2-repaired thumbnail checker after each thumbnail, gating the *move* into `READY-TO-POST` on their exit codes. (c) `run_daily.ps1` runs the full gate set after `cli run` and writes a PASS/FAIL block into `logs/run_<date>.log`, so an overnight failure is visible without asking. Each gate must first be proven to FAIL its negative control — an automated gate that cannot fail is worse than none, per F1.
COST: Low effort, a few hours total; (a) is ten minutes. Risk: turning on gates that currently fail their controls would block the pipeline, so F1/F2/F4/F5 must be fixed first — which is the correct order anyway.

## F7: All 97 tests pass, and not one of them touches a rendered artifact — the suite imports no ffmpeg, ffprobe, cv2, PIL or numpy, so the render, thumbnail and publish stages have zero automated coverage.

## F8: `make_short_auto.py` gate 4 ("no word-gap over 0.70s") measures its own remapped transcript rather than the rendered file, and the docstring justification for doing so does not reproduce at the parameters the gate itself uses.

SEVERITY: high
EVIDENCE: The gate at `scripts/make_short_auto.py:175-176` is `gaps = [words[i]["t"] - words[i-1]["t"] …]` where `words` is the list the same function built forty lines earlier at 127-134 by remapping `tr["words"]` through `timemap.json`. It is the script's own arithmetic checked against itself; the rendered output `a.out` is opened only for `pix_fmt`, `duration`, `width`, `height` and a decode pass (lines 170-178). No audio of the produced file is ever measured. The stated reason is the docstring at lines 14-18: *"DEAD AIR COMES FROM WORD GAPS, NEVER silencedetect. Measured on CARTHIEF at -30, -25, -20 AND -18 dBFS: zero spans every time. The courtroom room tone never drops that low, so the detector this repo used for every dead-air pass is blind here."* I re-measured that claim on `READY-TO-POST/CARTHIEF_SHORT.mp4` via `render.detect_silences` (default `min_silence_s=0.30`, src/boydclips/render.py:580-584) and it does not hold at the gate's own scale — at `min_silence_s=0.70`, the exact `--gap-min` default this gate uses: `-30.0dB → 16 spans, total 25.6s`; `-18.0dB → 10 spans, total 31.4s`. At `min_silence_s=0.18`: `-30.0dB → 27 spans, 29.6s`. The "zero spans" result reproduces only at `min_silence_s=4.0` with `-30dB` (`0 spans`), i.e. the 4-second CONTENT_SPEC threshold — a single parameter combination generalised into a blanket claim about the detector.
WHY-IT-MATTERS: Two consequences. First, the gate cannot detect the failure it is named for: if `tighten_short.py` writes a video that does not match the `timemap.json` it emitted — a cut dropped, an off-by-one segment, an ffmpeg concat that silently kept a span — the gate still passes, because it never looks at the video. It verifies a plan, and a plan is what the render is supposed to execute, not evidence that it did. Second, audio measurement was abandoned across the pipeline on the strength of the quoted claim, so `audit_cuts.py` (which uses the detector at 0.18s, where it demonstrably works) is treated as unreliable while the transcript-only path is treated as authoritative.
PROPOSAL: Keep the transcript check as a plan-sanity assertion but add the real gate on the rendered file: run `detect_silences(a.out, noise_db=-30, min_silence_s=<CONTENT_SPEC threshold>)` and fail on any span. Positive control measured in this audit: `CARTHIEF_SHORT.mp4` returns 0 spans at -30dB/4.0s. Negative control: the same file at 0.70s returns 16 spans totalling 25.6s, proving the gate can fail. Also correct the docstring to state the parameters the "zero spans" measurement was taken at — as written it reads as a property of the footage and has already propagated into two other design decisions.
COST: Low effort — one function call, both controls already measured here. Risk: it may fail existing renders, which is the point; STATE.md:184 already suspects "the long-forms were dead-aired with the blind silencedetect… almost certainly still carry gaps nobody measured."

## F9: `make_short_auto.py` gate 3 is labelled "A/V in sync" but compares only the two streams' durations, a quantity that is unchanged by any actual desync.

SEVERITY: medium
EVIDENCE: `scripts/make_short_auto.py:171-172` reads `vd = float(probe(a.out, "v:0", "duration"))` and `ad = float(probe(a.out, "a:0", "duration"))`, and line 183 is `("A/V in sync", abs(vd - ad) < 0.15, f"{vd:.2f}s / {ad:.2f}s")`. `probe()` at lines 66-71 requests only `stream=<field>` — `start_time` is never read, by this gate or anywhere in the file. Two streams of identical duration can be offset arbitrarily by a nonzero `start_time` or an mp4 edit list, both of which ffmpeg produces routinely when concatenating and re-encoding, and the gate is blind to all of it. Measured the three shipped finals to characterise the current state: `ffprobe -show_entries stream=codec_type,start_time,duration` gives CARTHIEF `video,0.000000,34.800000 / audio,0.000000,34.800000`, SANCHEZ `video,0.000000,49.133333 / audio,0.000000,49.141995`, OFFERUP `video,0.000000,41.900000 / audio,0.000000,41.890998`. All three happen to have `start_time=0`, so no desync is present today — but that is a property of these files, not something the gate established.
WHY-IT-MATTERS: The gate's name is the strongest claim in the whole verification block and it is the one with the least behind it — it asserts lip-sync while measuring stream length. Because it currently passes, it reads as evidence that sync has been verified across every short the routine produces, and a future ffmpeg or filter-chain change that introduces an edit-list offset would ship with a green "PASS A/V in sync" line printed next to it. This is the same class as the caption checker in Nathan's recorded lesson: keyed on a property the target shares with the failure.
PROPOSAL: Either rename it to "A/V durations match" — honest, cheap, and still worth checking — or make it measure sync. To measure it: read `start_time` for both streams and fail on `abs(v_start - a_start) > 0.05`, and additionally check for an edit list via `ffprobe -show_entries stream_side_data`. A true lip-sync gate needs a signature only sync has: cross-correlate the audio envelope against the frame-difference series that `who_speaks.py` already computes for this exact video (it runs at step 1/5 and its output is on disk as `speakers_full.json`), and require the peak at lag 0. Controls: positive any current final; negative the same file remuxed with `-itsoffset 0.3` on the audio, which is a one-command synthetic known-bad.
COST: Low for the rename plus `start_time` check (~10 lines). Medium for the correlation gate, but the correlation machinery already exists in `who_speaks.py` and the negative control is one ffmpeg command.

## F10: `make_short_auto.py` prints "REFUSED" and exits 4, but leaves the rejected file sitting in READY-TO-POST under its final name, so a refused render is indistinguishable on disk from an accepted one.

SEVERITY: high
EVIDENCE: The chain is: step 5/5 at `scripts/make_short_auto.py:157-161` invokes `caption_short.py` with `--out str(a.out)`, which writes the file; verification runs at 168-192; then line 193-194 `print("\n   " + (f"-> {a.out}" if ok else "REFUSED: a check failed above"))` / `return 0 if ok else 4`. Nothing between those lines deletes, renames, or quarantines `a.out`. The caller propagates the code correctly — `scripts/run_case.py:36-46` sets `ok = p.returncode == 0` and line 115-116 appends to `bad`, and `main()` returns 1 — but `a.out` is passed as `DESK / "READY-TO-POST" / f"{n}_SHORT_FINAL.mp4"` (run_case.py:113), so the rejected artifact lands in the publish-staging folder under the exact name a good one would have. `ls READY-TO-POST` confirms the folder is flat and mixed: `CARTHIEF_SHORT_FINAL.mp4`, `SANCHEZ_SHORT_FINAL.mp4`, `OFFERUP_SHORT_FINAL.mp4` sit beside `_CAP`, `_CLEAN`, `_TIGHT`, `_TIGHT_V2` intermediates with no status marker on any of them. I re-applied the four probe-measurable gates to all three finals and they currently pass (`pix_fmt=yuv420p 1080,1920 decode=clean`, duration deltas 0.000/0.009/0.009s), so no refused file is presently staged — but again, nothing on disk records that.

The refusal lives in a console exit code that vanishes when the terminal closes, while the artifact persists in the folder whose name means "ready to post". Since publishing is a manual step Nathan performs by picking a file out of that folder, the one place the refusal needed to be visible is the one place it is not — and CLAUDE.md's rule that anything built "must show its own state" is inverted here.
PROPOSAL: On failure, write the output to `READY-TO-POST/_REJECTED/<name>.mp4` and drop a `<name>.FAILED.txt` beside it containing the check table that was printed. On success, write a `<name>.PASSED.json` sidecar with each gate's measured value and the git rev — so the folder itself answers "is this verified?" without re-running anything. Better still, render to a staging dir and let `run_case.py` *move* into `READY-TO-POST` only on exit 0, which makes the gate structural rather than advisory.
COST: Low effort, ~15 lines across two files. Risk: none — it only adds a move and a sidecar. Requires deciding the quarantine path, which is Nathan's call on folder layout.

## F11: `check_vertical.py` and `audit_cuts.py` always exit 0 no matter what they find, and `check_vertical.py` does not implement the duplicate-half check its own docstring advertises.

SEVERITY: medium
EVIDENCE: Both end in a bare call: `tail -3 scripts/check_vertical.py` → `if __name__ == "__main__":     main()` and the same for `audit_cuts.py`, versus `raise SystemExit(main())` in `verify_set.py` / `verify_render.py` and `sys.exit(main())` in `verify_thumbnail.py`. `grep -n 'return' scripts/check_vertical.py` shows main's only return is the bare early-exit at line 73 — it never returns a status. So `print("  " + ("OK" if not flags else "PROBLEM: " + ", ".join(flags)))` at line 113 and `print("  UNPLAYABLE - no duration")` at line 85 both exit 0. Same for `audit_cuts.py:129`'s `f"\n{bad} of {len(rows)} cuts have a measurable problem."`. Ran `python scripts/check_vertical.py --samples 2` over the 14-file VERTICAL-FULL set: all reported OK, `EXIT=0` — consistent, but the code proves the exit is 0 regardless. Separately, the docstring at lines 8-11 promises two measurements per half: black fraction, and *"whether the two halves differ (a frame duplicated top and bottom means the grid was misread and the same tile was cropped twice)"*. `grep -n 'differ\|identical\|same tile\|corr\|diff' scripts/check_vertical.py` matches only those docstring lines — the comparison is not implemented anywhere; lines 99-104 compute `black_fraction(png,"top")` and `(png,"bottom")` and nothing else. Third defect: `black_fraction` returns `0.0` both on exception (line 59-60) and on no match (line 61), i.e. any parse failure reads as "not black" and passes.
WHY-IT-MATTERS: GATES.md's contract is *"A gate is met only when its CHECK exits zero and its EXPECT matches."* For these two scripts the first half of that contract is vacuous — they exit zero on their worst finding, so wiring either into a gate, a hook or `run_case.py` would create a gate that can never fail. The unimplemented duplicate-half check matters more than it looks: it is the specific detector for a misread Zoom grid, which is the failure mode `verify_render.py`'s docstring says shipped once already and which STATE.md's Blackburn case (72.2% coverage, "3-4 tile Zoom grid throughout") shows still occurs in the corpus. PROPOSAL: (a) `raise SystemExit(main())` on both, with `main()` returning 1 when any file flags. Positive control: any current VERTICAL-FULL file (all measured 0.0% black both halves, so all are genuine 2-ups). Negative control: synthesise one with `ffmpeg -vf "crop=iw:ih/2:0:0,vstack"` on a known-good file — a one-command known-bad. (c) Make `black_fraction` fail closed: return `None` on parse failure and treat `None` as a flag, not a pass.
COST: Low effort, ~25 lines total. Risk: the exit-code change may break any caller that ignores it today — grep shows there are none.

## F13: `tests/test_pipeline.py` writes a file into the current working directory when run under pytest, because pytest does not inject a fixture into a parameter that has a default value.

SEVERITY: low
EVIDENCE: `tests/test_pipeline.py:355` is `def test_caption_events_never_overlap(tmp_path=None):` and line 362 is `out = Path(tmp_path or ".") / "_overlap.ass"`. The author's intent is clear from the module docstring — the suite is designed to run both as `python tests/test_pipeline.py` and under pytest — but pytest excludes defaulted parameters from fixture resolution, so `tmp_path` stays `None` and the path resolves to `./_overlap.ass`. Verified against the installed version: `python -c "from _pytest.compat import getfuncargnames; def f(tmp_path=None): pass; print(getfuncargnames(f))"` → `()` on `pytest 9.1.1`. The file is removed at line 374, but that `out.unlink()` sits *before* the three assertions at 376-380, so it is skipped whenever the test fails — precisely when a stray artifact is most confusing. Three other tests use the same `tmp_path=None` idiom (476, and via `tempfile.mkdtemp()` at 508, 558) but those fall back to `tempfile.mkdtemp()` and are safe; this is the only one defaulting to `"."`. I ran the suite from the scratchpad with `-p no:cacheprovider` specifically to avoid writing `_overlap.ass` and `.pytest_cache/` into the repo during this audit.
WHY-IT-MATTERS: Minor on its own, but it blocks the cheapest fix in F6: a pre-commit hook running pytest would drop `_overlap.ass` into the repo root on every commit, and into whatever directory the developer happened to be in. Move `out.unlink()` into a `try/finally` so it runs on failure too. Add `_overlap.ass` to `.gitignore` as a belt-and-braces measure, and add `[tool.pytest.ini_options] testpaths = ["tests"]` to `pyproject.toml` so the suite has a defined entry point before it is hooked up.
COST: Trivial, ~6 lines, zero risk. Should be done before F6(a).
