## F1: Thumbnail impressions and CTR are NOT in the YouTube Analytics query API — they exist only as bulk Reporting API reports whose history starts the day you create the job, so no job means no data, ever.
SEVERITY: blocker
EVIDENCE: Fetched https://developers.google.com/youtube/reporting/v1/reports/channel_reports 2026-08-29 — "Reach reports provide statistics for video thumbnail impressions and click-through rates. The id for this report is `channel_reach_basic_a1`. Dimensions: date, channel_id, video_id. Metrics: `video_thumbnail_impressions`, `video_thumbnail_impressions_ctr`". These arrived per the revision history entry dated January 15, 2026. I then grepped the targeted-query metrics page https://developers.google.com/youtube/analytics/metrics for every impression token and got only adImpressions, annotationClickableImpressions, annotationClosableImpressions, annotationImpressions, cardImpressions, cardTeaserImpressions, totalSegmentImpressions — zero thumbnail metrics. https://developers.google.com/youtube/reporting/v1/reports states "You can start retrieving the report within 48 hours of the time that the job is created, and the first available report will be for the day that you scheduled the job" and "API reports are available for 60 days from the time that they are generated".
WHY-IT-MATTERS: The entire "background smart system that pays attention to what thumbnails work" depends on thumbnail CTR, and that number is unreachable from the API the local `youtube-channel` skill already targets. Worse, it is not retroactive: every day that passes without a `channel_reach_basic_a1` reporting job is a day of thumbnail CTR that can never be recovered, and reports older than 60 days are deleted server-side even after the job exists.
PROPOSAL: Today, as a one-off, create reporting jobs for `channel_reach_basic_a1` and `channel_basic_a3` via `jobs.create`, and add a daily cron that lists new reports by `createdAfter`, downloads the CSVs and appends them to a local store keyed by report id. Do not build any thumbnail-learning logic yet — build only the collector. Keep the Analytics query API for retention curves (F7); it cannot serve thumbnails.
COST: Half a day. Requires the OAuth setup in F7 plus the `yt-analytics.readonly` scope. Ongoing: one cron job and disk for daily CSVs; the 60-day server retention makes the local copy mandatory rather than optional.

## F2: The YouTube Data API quota model is not the shared 10,000-unit pool — search.list and videos.insert now have their own 100-calls-per-day buckets, which caps competitor polling at 100 API searches a day.
SEVERITY: high
EVIDENCE: Fetched https://developers.google.com/youtube/v3/determine_quota_cost 2026-08-29, verbatim: "Projects that enable the YouTube Data API have a default quota allocation of 100 search.list calls, 100 videos.insert calls, and 10,000 units per day combined for all other endpoints... The search.list and videos.insert methods have their own quota buckets. Each of these methods has a default daily limit of 100 per day. The quota cost is 1 per call." The method table on the same page reads `search list 100 quota per day. Each call costs 1 quota`, `videos list 1`, `videos insert 100 quota per day. Each call costs 1 quota`, `thumbnails set 50`, `playlistItems list 1`.
WHY-IT-MATTERS: Uploading is not the constraint — 100 uploads a day is unreachable for this channel. Discovery is. Any competitor-monitoring design that calls `search.list` per competitor per run burns the daily allowance in minutes. `videos.list` at 1 unit and `playlistItems.list` at 1 unit against the 10,000 pool are the cheap paths, and `thumbnails.set` at 50 units allows ~200 thumbnail swaps a day, so automated thumbnail replacement is not quota-constrained.
PROPOSAL: Never use `search.list` in a scheduled loop. Resolve each competitor channel's uploads-playlist id once, store it, then poll with `playlistItems.list` + `videos.list` (1 unit each). Better still, do competitor polling entirely outside the API — see F3.
COST: No effort beyond choosing the right endpoints. Requesting a quota increase is a Google audit form, not worth it given the free alternative in F3.

## F3: yt-dlp gives free, unquotaed, per-video competitor data — 30 videos with view counts in 0.75 seconds, plus maxres thumbnail images and full auto-transcripts — but it does NOT give the "most replayed" heatmap on these channels, which I verified rather than assumed.
SEVERITY: high
EVIDENCE: Ran `yt-dlp --flat-playlist --dump-json --playlist-end 30 https://www.youtube.com/@LawAndCrime/videos` on 2026-08-29 with yt-dlp 2026.07.04: returned 30 records with id, title, view_count and duration in `real 0m0.749s`, no API key, no quota. A full `--dump-single-json` on video yROy8yfU6_I returned 78 top-level keys including view_count=85769, like_count=666, comment_count=126, channel_follower_count, 45 thumbnail entries including `https://i.ytimg.com/vi/yROy8yfU6_I/maxresdefault.jpg`, tags, categories, upload_date, and 157 `automatic_captions` languages. Correction to my own expectation: the `heatmap` field (100 most-replayed points) was present on the 2005 control video jNQXAC9IVRw but I then sampled eight consecutive LawAndCrime videos and got `HEATMAP:none` on 8 of 8, and `chapters: 0` on 8 of 8.
WHY-IT-MATTERS: This is the whole realistic basis for "watch what competitors are doing". It can be built on: their thumbnail image files (downloadable and analysable), their titles, their view counts over time, their upload cadence, their durations, and their complete transcripts for free. It cannot be built on: most-replayed heatmaps, retention, impressions or CTR for anyone but himself. A design that assumed competitor retention data would have been building on nothing.
PROPOSAL: Build competitor monitoring as a nightly yt-dlp `--flat-playlist` snapshot per tracked channel, appended to a local table (channel, video_id, title, views, duration, first_seen, views_at_each_snapshot). Derive velocity by differencing snapshots — that is the only competitor "performance" signal that actually exists. Download `maxresdefault.jpg` for anything that outperforms its channel median, and keep them as a reference wall. Do not promise heatmap or retention comparisons.
COST: Low — yt-dlp is already installed. Ongoing maintenance is real: yt-dlp breaks when YouTube changes its player, so pin nothing and update it on a schedule. Rate-limit politely; this is scraping, not an API contract.

## F4: YouTube's July 2026 policy rework names "AI personas giving advice on sensitive topics ... legal issues" as a specific non-monetizable category — which is the exact shape an unattended AI-narrated court channel would take.
SEVERITY: blocker
EVIDENCE: https://www.tubefilter.com/2026/07/13/youtube-inauthentic-content-monetization-policy-update/ (published 2026-07-13) names the three official categories as "Generic or Repetitive Content", "Unsatisfying or Off-putting Content", and "AI Personas Related to Sensitive Topics", and states "The rules themselves haven't changed, and creators are not facing demonetization for new reasons." https://techcrunch.com/2026/07/20/youtube-clarifies-policies-around-ai-slop-and-upsetting-videos/ (published 2026-07-20) reports YouTube does not want to "incentivize creators using AI personas to discuss more sensitive topics, like finance, legal issues, healthcare, and medical issues", and category one as "repetitive content, such as material that can be easily made with AI, computer-generated imagery (CGI), or templates, with little variation". The underlying help page https://support.google.com/youtube/answer/1311392 (fetched 2026-08-29) shows a last-updated date of July 15, 2025 and prohibits "content that appears to be produced using a template or where each video doesn't deliver creative, educational, or other value to the viewer".
WHY-IT-MATTERS: Two of the three named categories are exactly what an unattended pipeline produces by default. A fixed template applied to every hearing is "generic or repetitive". An AI voice explaining what a ruling means is an "AI persona ... on legal issues". The goal of removing the human from the loop and the goal of staying monetized pull in opposite directions, and the policy reviews the channel's pattern across uploads, not one video.
PROPOSAL: Do not build AI narration or an AI host into the pipeline at all — it is the one named category this channel would land in. Keep the value-add human and non-synthetic: real courtroom audio, factual on-screen context from the actual case record, and Nathan's own written framing. Deliberately vary structure across uploads rather than locking one template, and treat "every video opens identically" as a defect the QC step should flag, not a feature.
COST: Zero build cost; it is a constraint on the design, and it removes the most tempting automation (auto-narration). Ongoing cost is variety, which is at odds with full unattendedness — accept a template *library* rather than a template.

## F5: The policy that actually governs a court-clip channel is "reused content", not the AI rules — and it was explicitly left unchanged in July 2026, which means the monetization question is "what did you add", answered per video.
SEVERITY: high
EVIDENCE: https://support.google.com/youtube/answer/1311392 (fetched 2026-08-29) draws the line at whether "the bulk of your content is different" and permits "similar content ... in which each video has a distinct storyline, focus, or concept", while prohibiting "similar or repetitive content with low educational value, commentary, narratives, or minimal variation across videos". The July 2026 reporting is consistent that the reused-content policy — the one covering commentary, clips, compilations and reaction videos — was not changed by the inauthentic-content rework (Tubefilter 2026-07-13, above).
WHY-IT-MATTERS: Public court video being public information is not the monetization question; the monetization question is transformation. A pipeline that downloads a livestream, cuts it and uploads it with burned captions has added editing but very little else, and that is the weakest defensible position. This is a design constraint on the automated pipeline, not a legal-rights question.
PROPOSAL: Make the transformation step a mandatory, non-skippable stage of the pipeline rather than an optional garnish: per-video written context (charge, case posture, what the ruling means factually), substantive selection with a stated reason, and on-screen information that does not exist in the source stream. Have the pipeline refuse to mark a render ready if that stage is empty — see F8.
COST: This is the part that cannot be fully automated, and pretending otherwise is the trap. Budget it as a five-minute human input per video, which is compatible with "not much of any input" but not with zero.

## F6: Native A/B testing exists, allows three title/thumbnail variants, and picks the winner by watch time rather than CTR — but it has no API and does not work on Shorts, so it cannot be part of an unattended loop.
SEVERITY: medium
EVIDENCE: https://support.google.com/youtube/answer/16391400 fetched 2026-08-29: creators can test "up to three thumbnails and/or titles to test"; "the title or combination of title and thumbnail with the highest watch time will be shown to all viewers"; "Your test should be completed within two weeks", varying with impressions; eligibility is YouTube Partner Program plus advanced features, "Desktop only (YouTube Studio)"; not available for Shorts, scheduled lives or Premieres, and unavailable for made-for-kids, mature or private videos; a control group is held out; and "If a title or thumbnail is manually changed during testing, the test will automatically stop". No corresponding method appears in the Data API method table at https://developers.google.com/youtube/v3/determine_quota_cost (fetched 2026-08-29) — `thumbnails.set` is a plain replace at 50 units.
WHY-IT-MATTERS: The best thumbnail-learning instrument YouTube offers is a manual, desktop-only, human-driven feature. Anything the pipeline "learns" about thumbnails is strictly worse-powered than just running Test & Compare by hand. Also note it optimises watch time, not clicks — so a "learn what thumbnails get clicks" system would be optimising a different objective than YouTube's own tool.
PROPOSAL: Make thumbnail A/B a human ritual, not a pipeline feature: have the pipeline generate three thumbnail variants per long-form video and drop them in a folder, and Nathan uploads them into Test & Compare in Studio. Record the winner back into the local store. Build no automated thumbnail optimiser. Note Shorts are excluded entirely, so no thumbnail testing exists for the Shorts half of the channel.
COST: Generating three variants instead of one is cheap. The manual Studio step is a few clicks per video. Gated on YPP eligibility.

## F7: The retention curve — the one feedback signal that is genuinely available per video today — is already wired up in a local skill, and the only thing blocking it is that no OAuth credential exists on this machine.
SEVERITY: high
EVIDENCE: Read `C:\Users\natha\.claude\skills\youtube-channel\SKILL.md` on 2026-08-29: it targets `GET https://youtubeanalytics.googleapis.com/v2/reports` and prints "the absolute retention curve — `audienceWatchRatio` against the `elapsedVideoTimeRatio` dimension — plus `relativeRetentionPerformance`", and states "There are no credentials on this machine — verified 2026-08-29, no `client_secret*.json` anywhere under `~/Projects`". I verified those identifiers against the live docs: https://developers.google.com/youtube/analytics/dimensions (fetched 2026-08-29) — "elapsedVideoTimeRatio ... The API returns 100 data points for each video with ratio values ranging from 0.01 to 1.0 ... for a two-hour video, the interval between data points is 72 seconds"; grep of the fetched metrics page confirms audienceWatchRatio and relativeRetentionPerformance are present (1 and 3 occurrences).
WHY-IT-MATTERS: Retention is the only per-video, per-moment feedback signal this channel can get from the API, and it is exactly the signal that tells you whether the automatic moment-scoring picked the right moment. It is also the signal that degrades on long-form: 100 fixed points means a 90-minute hearing is sampled every 54 seconds, so the curve cannot tell you which 5-second cut lost people. On a 60-second Short each point is 0.6s, which is usable.
PROPOSAL: Do the OAuth setup once — it is a single human step and it unblocks both this and F1. Then, after each upload, store the 100-point retention curve alongside the cut list that produced the video, so that later there is a joined dataset of "we cut here, viewers left there". Storing the join is the work; learning from it comes later.
COST: One human session in Google Cloud console (create project, enable YouTube Data API v3 and YouTube Analytics API, desktop OAuth client, consent once). Free tier. No ongoing cost beyond token refresh.

## F8: Automated render QC needs nothing installed — the ffmpeg already on this machine has blackdetect, freezedetect, silencedetect, scdet, signalstats, ssim, psnr and libvmaf compiled in.
SEVERITY: high
EVIDENCE: Ran `ffmpeg -version` on 2026-08-29: `ffmpeg version 8.0.1-essentials_build-www.gyan.dev`, configuration line includes `--enable-libvmaf --enable-libzimg --enable-libass --enable-nvenc`. Ran `ffmpeg -filters` and confirmed each of: `blackdetect` (Detect video intervals that are (almost) black), `freezedetect` (Detects frozen video input), `silencedetect` (Detect silence), `blackframe`, `cropdetect`, `libvmaf` (Calculate the VMAF between two video streams), `ssim`, `psnr`, `signalstats`, `scdet` (Detect video scene change), `entropy`. Netflix/vmaf itself is at 5462 stars, last pushed 2026-08-14, licence field NOASSERTION per the GitHub API on 2026-08-29 — but it is reached here through ffmpeg's own build, not vendored.
WHY-IT-MATTERS: "Prove a render is good without watching it" is the single hardest requirement in an unattended pipeline, and the answer is not an AI reviewer — it is a small set of deterministic assertions that fail loudly. This is available today at zero cost and is the difference between a pipeline that can be trusted to run unattended and one that cannot.
PROPOSAL: Add a hard QC gate after every render that fails the artifact rather than warning: `blackdetect` finds no black run longer than ~0.5s inside the body; `freezedetect` finds no frozen segment; `silencedetect` finds no silence run longer than ~2s where speech was expected from the transcript; `ffprobe` confirms duration within tolerance of the cut list, exact resolution (1080x1920 for the Short), expected fps and that an audio stream exists with non-silent loudness; and a burned-caption check by sampling frames at known caption timestamps. Reserve `libvmaf`/`ssim` for the narrower question of whether re-encode settings degraded the master, comparing render against source — not as a general "is it good" score.
COST: A day to write, then near-zero. Deterministic and fast. The judgement is in choosing thresholds; tune them against the existing renders as fixtures rather than guessing.

## F10: Every "active speaker tracking" reframing tool in this space is built on Ultralytics YOLO, which is AGPL-3.0 and whose vendor explicitly claims the licence applies even to purely internal use.
SEVERITY: high
EVIDENCE: `ultralytics/ultralytics` via GitHub API 2026-08-29: 61061 stars, pushed 2026-08-29, licence AGPL-3.0. https://www.ultralytics.com/license fetched 2026-08-29 states that AGPL-3.0 compliance means "publicly releasing the complete corresponding source code for the entire derivative work, including the larger application, modifications, scripts, configuration files, and, where applicable, model weights", that an Enterprise License is needed for "Internal business tools or private company applications" and "Any commercial product or service", and that this applies "even if you train your own model from scratch" or if you "use YOLO only internally or for R&D". By contrast `google-ai-edge/mediapipe` is Apache-2.0, 36764 stars, pushed 2026-08-29, and the reframing repos in F9 use MediaPipe FaceMesh alongside YOLO for the speaker decision. Against the vendor's reading, the AGPL-3.0 text itself, fetched from https://www.gnu.org/licenses/agpl-3.0.txt on 2026-08-29, conditions section 13 on "if you modify the Program, your modified version must prominently offer all users interacting with it remotely through a computer network... an opportunity to receive the Corresponding Source", and defines conveying as "any kind of propagation that enables other parties to make or receive copies. Mere interaction with a user through a computer network, with no transfer of a copy, is not conveying."
WHY-IT-MATTERS: Ultralytics' stated reading is aggressive and is contradicted by the licence text quoted above — unmodified, private, non-networked use neither conveys nor triggers section 13 — but it is the vendor's published position and it is the position they would litigate from. Since this is a monetised operation and the pipeline is never distributed, the exposure is low; but it is not zero, and it is entirely avoidable.
PROPOSAL: Do not put Ultralytics YOLO in this pipeline. For a fixed courtroom camera the subject positions are near-static, which makes the whole active-speaker-tracking apparatus unnecessary: derive the crop window from a handful of manually-defined named regions (bench, defence table, podium, witness box) and switch between them using the diarised speaker label from F11. That is more accurate than a tracker on this footage and carries no licence question. If face detection is genuinely needed, use MediaPipe (Apache-2.0).
COST: Defining the regions is a one-off per camera layout and must be redone if the court changes its setup. It removes a large dependency and a whole class of tracking failures.

## F11: For word-level alignment and diarisation the live, commercially-safe stack is WhisperX (BSD-2) plus pyannote (MIT but access-gated); stable-ts, a common choice for this, was archived on 2026-05-30.

Do not adopt stable-ts — it is archived. Note faster-whisper has not been pushed in nine months; if WhisperX's dependency on it becomes a problem, `achetronic/parakeet` (Apache-2.0) is the live alternative.
COST: WhisperX and pyannote both need a GPU to be practical, which this machine has. One-time HF account and condition acceptance. Ongoing: pin versions, because WhisperX's stack moves.

## F12: The orchestration pattern serious operators use is durable execution — checkpoint each step's output, require steps to be idempotent, resume from the first uncheckpointed step — and there are three permissively-licensed engines that implement it.
SEVERITY: medium
EVIDENCE: https://docs.dbos.dev/architecture fetched 2026-08-29: "Every workflow input and step output is durably stored in the system database"; on restart the workflow "re-executes with checkpointed inputs, skipping steps with cached outputs" and "the recovered workflow reaches a step with no checkpoint. This marks the point where the original execution failed"; steps "must be idempotent — safe to retry multiple times"; "once a step completes and is checkpointed, it is never re-executed"; workflows must be deterministic, with all non-determinism (API calls, timestamps, randomness) confined inside steps. Cost is stated as "one database write per step ... plus two additional database writes per workflow". Engine survey via GitHub API 2026-08-29: `dbos-inc/dbos-transact-py` 1554 stars MIT pushed 2026-08-28; `hatchet-dev/hatchet` 7809 stars MIT pushed 2026-08-29 ("orchestration engine for background tasks, AI agents, and durable workflows"); `PrefectHQ/prefect` 23714 stars Apache-2.0 pushed 2026-08-28; `apache/airflow` 46631 stars Apache-2.0 pushed 2026-08-29.
WHY-IT-MATTERS: This is the real answer to "run without me putting in much of any input" — not intelligence, but recoverability. A three-hour hearing that fails at the burn-in step after ninety minutes of transcription must resume at burn-in, not restart. The rule that makes it work is architectural and free: every step writes to a path derived from a hash of its inputs, checks for that path first, and returns it if present. That gives idempotency, resumability, content-addressed artifacts and provenance in a single mechanism.
PROPOSAL: Adopt the pattern before adopting any engine. Make each pipeline stage a pure function of (input artifact hash + parameters hash) writing to `artifacts/<stage>/<hash>/`, with a sidecar JSON recording tool versions, parameters, input hashes and wall time. That alone delivers resumable and reproducible runs with no dependency. Only if that proves insufficient, wrap it in DBOS (MIT, needs Postgres) — do not reach for Airflow, which is a scheduler for data teams and is far heavier than one channel needs.
COST: A day or two to restructure existing stages into the hash-addressed shape, and it is genuinely a restructure, not a bolt-on. Disk grows since artifacts are never overwritten — add a retention sweep. Zero licence risk; all four engines are MIT or Apache-2.0.

## F13: With ~2 videos, no thumbnail or title learning is statistically possible — I measured a 22.5x view spread across one competitor's 30 most recent videos, and topic swamps every production variable in that data.
SEVERITY: blocker
EVIDENCE: Measured 2026-08-29 via `yt-dlp --flat-playlist --dump-json --playlist-end 30 https://www.youtube.com/@LawAndCrime/videos`, n=30, median 163,000 views, max/min ratio 22.5. Top 5: 652,000 (2636s, "Lindsay Clancy Case: Disturbing Timeline Emerges"), 571,000 (1518s), 565,000 (1577s), 367,000 (1592s), 363,000 (1810s). Bottom 5: 68,000 (1316s), 62,000 (1800s), 57,000 (3703s), 33,000 (1350s), 29,000 (1206s, "Dad Shoots Child's Alleged Rapist Then Ends Up Behind Bars: Cops"). Duration does not separate them — the second-longest video in the sample (3703s) is in the bottom five while the longest top performer is 2636s. Corroborating the same point from YouTube's own side: https://support.google.com/youtube/answer/16391400 (fetched 2026-08-29) says a native A/B test on a single video "can take a few days or up to two weeks to complete due to differences in impressions" — YouTube needs that much traffic on one video to separate three variants.
WHY-IT-MATTERS: This is the honest answer to the "self-learning" part of the goal. An established channel with hundreds of thousands of views per video shows a 22.5x spread driven by which case it covers. Against that noise, a thumbnail-font or title-formula effect is undetectable without a large number of videos, and YouTube's own instrument — which has access to every impression and a randomised control group — still needs up to two weeks on one video. Any "smart system that learns what thumbnails work" built on two videos is not learning, it is fitting noise and then acting on it, which is worse than doing nothing because it will confidently change things that were fine.
PROPOSAL: Build the collector, not the learner. Store, per video: the exact thumbnail file, title, chosen moments with scores and reasons, publish time, and then the daily reach CSV (F1) and retention curve (F7) joined to it. Write no adaptation logic. Revisit at roughly 30 videos, and even then the first honest analysis is descriptive — rank by CTR and by retention, look at the top and bottom five *from this channel*, and let Nathan's eye read them. That is the same method that produced the table above, and it works at n=30.
COST: Storage and discipline only. The cost of the alternative — building an adaptive system now — is real: it is wasted build time plus a system that will make confidently wrong changes.

## F15: The impressive-sounding version of this — an adaptive system that watches competitors and tunes itself — is not what should be built; the evidence points at a boring, resumable pipeline with hard gates and a data collector that learns nothing yet.
SEVERITY: blocker
EVIDENCE: This is the synthesis of the findings above, each of which carries its own fetched source: thumbnail CTR is only collectable, not queryable, and only from the day a job is created (F1, developers.google.com/youtube/reporting/v1/reports, fetched 2026-08-29); competitor performance data beyond public view counts does not exist to be observed — heatmap absent on 8 of 8 sampled videos measured 2026-08-29 (F3); the measured signal-to-noise on a mature channel in this niche is 22.5x driven by case selection (F13); YouTube's July 2026 policy names template-driven output and AI legal personas as non-monetizable (F4, tubefilter.com 2026-07-13 and techcrunch.com 2026-07-20); and the two things that are unambiguously available and cheap today are deterministic render QC via the already-installed ffmpeg 8.0.1 (F8, `ffmpeg -filters` run 2026-08-29) and durable checkpointed execution (F12, docs.dbos.dev/architecture fetched 2026-08-29).
WHY-IT-MATTERS: The stated goal has two halves and they have very different evidence behind them. "Smart enough to run without much input" is well-supported and buildable now — it is an engineering problem about resumability and verification, and every piece is available and permissively licensed. "Some self-learning" and "watch what competitors do" are, on the current evidence, mostly not buildable: the data either does not exist (competitor retention, competitor CTR), does not exist yet (his own thumbnail CTR, which starts accruing only once a job is created), or is too noisy at this channel size to learn from. Building the second half now consumes the effort the first half needs and produces a system that acts on noise.
PROPOSAL: Build in this order. (1) Create the reporting jobs today so the CTR clock starts, and do the one-time OAuth setup — these are the only irreversible-if-delayed items. (2) Restructure the pipeline into hash-addressed, resumable stages with per-artifact provenance. (3) Add the ffmpeg QC gate that fails renders rather than warning. (4) Add the yt-dlp nightly competitor snapshot as pure data collection with no logic on top. (5) Generate three thumbnail variants per video for Nathan to put through Test & Compare by hand. Explicitly do NOT build: AI narration or an AI host (F4), an automated thumbnail optimiser (F6, F13), anything depending on competitor retention or heatmaps (F3), or any adaptive rule fitted on fewer than ~30 videos (F13). The one irreducibly human step is the transformation that keeps the channel monetizable under the reused-content policy (F5) — design the pipeline to stop and ask for it rather than to fake it.
COST: Roughly a week of build for items 2-5, plus one human session for item 1 that should happen today because its value decays daily. Ongoing: yt-dlp updates, pinned model versions, and a disk retention sweep. The deliberate omissions cost nothing now and can be revisited at ~30 videos with real joined data in hand, which is a far better position than guessing today.
