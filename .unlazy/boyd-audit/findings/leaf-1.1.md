# leaf-1.1 — ingest, transcription and the store

## F1: The daily ingest is not scheduled and has never run — no Windows task named BoydClips exists, and the newest docket in the store is 16 days old
SEVERITY: blocker
EVIDENCE: `Get-ScheduledTask -TaskName 'BoydClips'` -> "NO SCHEDULED TASK NAMED BoydClips: No MSFT_ScheduledTask objects found"; `Get-ScheduledTask | Where TaskName -match 'boyd'` -> empty. `ls logs/run_*.log` -> only run_2026-08-14.log and run_2026-08-14b.log; `grep -c "boyd-clips daily run" logs/*.log` -> zero matches in every file, so run_daily.ps1:23 (Write-Log "=== boyd-clips daily run ===") has never appended to any log and those two files were written by a bare `cli run`, not by the driver. sqlite3 `SELECT MAX(docket_date) FROM dockets` -> 2026-08-13, against today 2026-08-29.
WHY-IT-MATTERS: No video goes out at all. Every docket published by the court since 2026-08-14 is un-ingested, and because `discover.filter_new` drops anything older than `source.max_age_days: 4` (config/pipeline.yaml), those 15 days are already permanently unreachable through `boyd run` even if the scheduler is registered today — they can only be recovered by hand via scripts/pull_archive.py plus `boyd run --case`.
PROPOSAL: Register the schtasks line from run_daily.ps1:3-4, and add a `boyd doctor` check that fails when MAX(docket_date) in dockets is more than 3 days behind today, so a dead scheduler is visible in the health output rather than only in the absence of new videos.
COST: Registering the task is minutes. The doctor check is ~15 lines; it risks failing legitimately on court holidays and long recesses, so it should warn rather than exit 1 unless the gap exceeds a week.

## F2: `cli run` exits 0 when it produces nothing, so run_daily.ps1 logs "run complete" and reports success on a run where every docket failed
SEVERITY: blocker
EVIDENCE: src/boydclips/cli.py:140-142 — `if not results: print("\nno clips produced this run"); return 0`. run_daily.ps1:38-41 — `if ($LASTEXITCODE -ne 0) { throw ... }` then Write-Log "=== run complete ==="; exit 0. Measured against a real run: logs/run_2026-08-14.log shows "discover: 8 streams listed, 7 new and eligible" followed by "production failed: command failed: yt-dlp ... HTTP error 403 Forbidden ... ERROR: ffmpeg exited with code 3436169992" and "WARNING docket left pending" on every docket; pipeline.py:720-723 and :781-784 catch those and `continue`. Zero clips were produced and the process still exits 0.
WHY-IT-MATTERS: A total outage — stale yt-dlp, YouTube 403ing every download, a revoked cookie — is indistinguishable from "the court had a quiet day". Nothing surfaces it, so the channel silently stops publishing and nobody finds out until someone opens YouTube.
PROPOSAL: Return a distinct non-zero code from `cmd_run` when discover() returned dockets but zero clips were produced (a genuinely empty channel day, where `new` is empty, stays 0), and have run_daily.ps1 treat that code as a failure worth alerting on.
COST: ~10 lines in cli.py plus a branch in run_daily.ps1. Risk: dry runs and days where all cases fail the safety gate would now exit non-zero, so the "no eligible cases" case must be excluded explicitly or the scheduler will cry wolf.

## F3: 48 dockets are permanently untranscribed because scripts/pull_archive.py calls fetch_captions directly and bypasses the Whisper fallback that config enables
SEVERITY: high
EVIDENCE: 1760 dirs under work/, 59 without a *.transcript.json; 11 of those are scratch dirs (_L1, _audit, _edits, _variants, edge, pacing-evidence, q1-q4, smoketest) and the remaining 48 are 11-char video-id dirs that are completely empty (0 files). Loading state/archive_failed.json gives 48 entries with reason histogram Counter({'no captions available': 48}), and the set of failed ids equals the set of empty dirs exactly (measured: failed==empty? True, 0 in either difference). scripts/pull_archive.py:111-115 calls fetch_captions(vid, work) and on `tr is None` records "no captions available" and moves on; it never calls get_transcript, which is the only function that honours `transcription.whisper_fallback: true` — and faster_whisper IS installed here (`importlib.util.find_spec('faster_whisper')` -> True). state/archive_pull.json records "ok": 821, "failed": 48, "done": 869, so the sweep considers itself finished.
WHY-IT-MATTERS: 48 court days, spread from 2021-04-09 to 2026-05-29, are invisible to every selection and scoring stage. The failure is recorded in a JSON file nothing reads and nothing re-drives; re-running pull_archive.py would retry them and fail identically, forever, because the reason is structural (no captions on YouTube), not transient.
PROPOSAL: Have pull_archive.py call get_transcript instead of fetch_captions so the configured Whisper fallback fires, or add an explicit --whisper-missing sweep that walks state/archive_failed.json and runs transcribe_whisper on each. Also delete the empty work dir on failure so "empty dir" stops being an ambiguous state.
COST: Low code cost (a one-line call change plus a flag). Real cost is compute: 48 streams averaging 2-3 hours of audio through faster-whisper `medium`, roughly a day of GPU time, and it sets Transcript.source to whisper:medium for those, which downstream word-timing consumers have never been tested against (0 of 1701 current transcripts came from Whisper).

## F4: 821 of 1701 stored docket dates come from YouTube's upload_date, and 412 of the 464 that can be cross-checked are exactly one day later than the real courtroom date
SEVERITY: high
EVIDENCE: Comparing dockets.docket_date against discover.parse_docket_date(title) — 821 rows differ because the title does not parse and pull_archive.py:82 filled them from discover.fetch_upload_date. Cross-checking those against the weekday word still present in the title (e.g. "TUESDAY 04/25/2023 DOCKET" stored as 2023-04-26): 464 are checkable and the offset histogram is {0: 50, 1: 412, 2: 1, 5: 1} — 89% are +1 day. Independent confirmation from the weekday distribution: title-parsed rows are Sat 0.2% / Mon 24.0%, upload-date rows are Sat 9.5% / Mon 4.8%, i.e. 78 phantom Saturday "dockets" and Monday nearly vanishing — the signature of a Central-time afternoon stream crossing into the next UTC day.
WHY-IT-MATTERS: docket_date is passed straight into `meta` at pipeline.py:139 and reaches titles, descriptions and any date-based dedup. A long-form captioned "Aug 5" when the hearing was Aug 4 is checkable against the court's own public listing and reads as sloppy on a channel whose whole premise is public-record accuracy.
PROPOSAL: Extend _DATE_RE to also read numeric forms (MM/DD/YYYY and MM-DD-YYYY — 31 titles carry one and 30 of those currently fail to parse), and when falling back to upload_date use %(release_date)s or %(timestamp)s converted to America/Chicago rather than the UTC %(upload_date)s. Backfill the 821 existing rows.
COST: Regex plus a timezone conversion, maybe an hour. The backfill needs one metadata request per affected video (821 requests, paced) or a one-off correction using the title weekday where present. Risk: rows already used to name rendered clips would change, so re-dating must not silently rewrite anything already in `clips`.

## F5: apply_phrase_fixes runs only inside get_transcript, so 57% of the cached corpus still says "bear county" and every script that reads the transcript JSON directly inherits it
SEVERITY: high
EVIDENCE: `grep -rn "apply_phrase_fixes" src scripts` -> the only call sites are transcribe.py:273 and :289, both inside get_transcript. scripts/pull_archive.py:117 writes tr.to_json() straight from fetch_captions, skipping the fix. Measured on a random sample of 250 of the 1702 transcripts on disk: 143 files (57%) still contain the literal phrase "bear county", 490 occurrences in total. Readers that bypass the fix include scripts/rerender_short.py:112 (Transcript.from_json(...) -> render.build_ass -> burned-in captions), scripts/caption_short.py:314 (json.load(open(a.transcript))), scripts/make_short.py:260, plus rescore.py, top_picks.py, find_hearings.py, rank_hearings.py and judge_*.py which feed the scoring models.
WHY-IT-MATTERS: transcribe.py:213-217 states the reason itself — Bexar is the county's name, it reaches burned-in captions, titles, descriptions and the text the scoring model reads, and local viewers notice immediately. The main `boyd run` path is currently safe (all 16 video ids with rendered clips have clean transcripts, measured: 0 still containing the phrase), but the moment a short is cut, using rerender_short.py or caption_short.py, from any of the ~970 transcripts (57% of 1701) that still carry the phrase, "Bear County" is burned into the frame.
PROPOSAL: Apply the fix inside Transcript.from_json rather than in get_transcript, so every reader gets it, and run a one-off sweep over work/*/*.transcript.json to normalise the cache on disk.
COST: Two-line move plus a sweep script; ~30 minutes. Risk: from_json becomes mutating-on-read, and any test that round-trips a transcript containing the literal phrase changes behaviour. The equal-token-count constraint at transcribe.py:240-241 keeps timings aligned, so the sweep is timing-safe.

## F6: The analysis backfill can only see 350 of the 1701 transcripts, and re-running its index generator cannot recover the rest
SEVERITY: high
EVIDENCE: scripts/backfill_analyse.py:41-45 reads state/archive_transcripts.json and errors out if it is missing. That file holds 350 rows (newest date 2026-08-10, mtime 2026-08-11 04:56:23) against 1701 transcript dirs on disk — 1351 transcripts, 79% of the corpus, are absent from the only index the analysis backfill consults. Re-running its generator does not fix this: scripts/backfill_transcripts.py:28 defaults `limit = 400` and line 37 keeps only `[d for d in discover.list_recent(url, limit) if d.docket_date]`, i.e. only title-parseable dates — and only 879 of the 1701 stored titles parse at all, so even --limit 2500 caps the index at ~880.
WHY-IT-MATTERS: The whole point of pull_archive.py (its docstring: "the selection stage has been choosing from a fifth of what exists") was to widen the pool. That gain never reached analysis — the case library is still built from a small, date-biased slice, and the best material on the channel may simply never be looked at.
PROPOSAL: Drop the JSON index entirely and have backfill_analyse.py enumerate work/*/*.transcript.json directly, joined to `dockets` for date and title, with the MIN_WORDS = 3000 filter applied from the transcript itself.
COST: ~20 lines in backfill_analyse.py. Risk: the todo list jumps from 350 to ~1590 dockets over 3000 words, so the LLM spend of a full backfill rises roughly fivefold — that needs to be a deliberate, confirmed decision, not a side effect.

## F7: Cached-analysis reruns never stamp the docket, so dockets.status under-reports work that has been done
SEVERITY: medium
EVIDENCE: pipeline.py:104-119 — analyze_docket returns from the work/<id>/scored.json cache before reaching `self.store.mark_docket(docket.video_id, "transcribed", ...)` at line 138 and "analyzed" at line 166. Consequence measured in the store: 45 dirs hold a scored.json, 47 video ids have rows in `cases`, but only 44 dockets have a non-null analyzed_at. Two dockets processed from cache on 2026-08-14 (UtydTa4kZhk and 0siAjhcOQF8, both visible in logs/run_2026-08-14.log as "analysis: reusing cached result") are still status='discovered' with transcribed_at IS NULL despite having a full transcript and scored cases on disk. Two other video ids (W8IvfROpZc8, zHchVGBX9iA) have `cases` rows with no scored.json at all.
WHY-IT-MATTERS: status is the field pending_dockets() and backfill_analyse.py's `done` set both key off. A docket that is fully analysed but reads 'discovered' gets re-queued and re-analysed; one that reads 'analyzed' with no cache is skipped by backfill_analyse's scored.json check while the pipeline silently redoes its LLM work. Neither loses a video, but both waste model spend and make the ledger an unreliable picture of pipeline state.
PROPOSAL: Move the two mark_docket calls so they also fire on the cache-hit path, next to the existing save_case re-assertion block at pipeline.py:113-118 which exists for exactly this class of bug.
COST: Three lines. Low risk — mark_docket is an idempotent UPDATE.

## F8: 4.65 GB of redundant json3 caption files sit in work/ because fetch_captions never deletes its downloads and the only thing that would is a destructive whole-dir sweep
SEVERITY: low
EVIDENCE: glob('work/*/*.json3') -> 2702 files totalling 4650.7 MB, versus 778.0 MB for all 1702 *.transcript.json. Every one of the 1351 dirs that has them has exactly two — <id>.en.json3 and <id>.en-orig.json3 — because transcribe.py:106-119 passes both --write-auto-subs and --write-subs and never deletes the downloads after parse_json3 at line 133. Measured on 25 randomly chosen dirs, the two tracks parse to identical word text in 25/25 cases, so the second copy carries no information. The only reclaimer is Pipeline.cleanup (pipeline.py:921-936), which does not run per-fetch — it is invoked from cmd_run/cmd_cleanup, and by F1 neither has run since 2026-08-14.
WHY-IT-MATTERS: 4.65 GB of pure duplication on the working disk, growing about 3.4 MB per docket forever, on a machine that also has to hold multi-gigabyte video sections during rendering. Reclaiming it currently requires the blunt cleanup pass, which as F11 shows also destroys the analysis cache.
PROPOSAL: Delete the .json3 files in fetch_captions itself once parse_json3 has succeeded and the transcript has been written, so reclamation is immediate and does not depend on the destructive sweep; add a one-off pass for the 2702 already on disk.
COST: Two lines plus a sweep. Risk: it removes the ability to re-parse a caption track offline if parse_json3 is later improved — keeping en.json3 and deleting only en-orig.json3 still reclaims ~2.3 GB if that matters.

## F9: The store opens SQLite with no busy timeout and in rollback-journal mode, so two boyd processes at once fail immediately instead of waiting
SEVERITY: medium
EVIDENCE: `grep -n "busy_timeout|WAL|isolation_level|timeout" src/boydclips/state.py` returns nothing; state.py:105-107 is `sqlite3.connect(db_path)` followed only by `PRAGMA foreign_keys = ON`. Measured directly against the project's own Store class on a throwaway db in scratch: `PRAGMA journal_mode` -> delete, `PRAGMA busy_timeout` -> 5000, and with one Store holding a BEGIN IMMEDIATE the second Store's add_docket() raised `OperationalError: database is locked` after 6.0s. `PRAGMA journal_mode` on the real state/pipeline.db also returns `delete`. Concurrent use is a real pattern here, not hypothetical: scripts/pull_archive.py:65 opens its own Store(ROOT/"state"/"pipeline.db") while the pipeline may be running, and logs/run_2026-08-14.log and run_2026-08-14b.log show two `cli run` invocations five minutes apart on the same day.
WHY-IT-MATTERS: A pull_archive sweep paces at 1.5-2.2s per video over hundreds of videos, so overlapping it with the daily run means the 5-second window is exceeded and add_docket/mark_docket raise. pipeline.py:720-723 catches that and writes status='error' on a docket that was fine; the docket is then aged out by max_age_days four days later and lost.
PROPOSAL: Set PRAGMA journal_mode=WAL and PRAGMA busy_timeout=30000 in Store.__init__. (The database passed PRAGMA integrity_check -> ok and PRAGMA foreign_key_check -> 0 rows, so there is no existing damage to repair.)
COST: Two lines. WAL adds -wal and -shm sidecar files that must be included in any backup or copy of the db, and .gitignore should cover them.

## F10: Multi-session days and store-vs-disk agreement are both sound; the residual coverage risk is scan_depth 8 being narrower than the 4-day age window
SEVERITY: low
EVIDENCE: discover.parse_session plus SESSION_ORDER (discover.py:26-29) sort morning before afternoon chronologically rather than alphabetically, and list_recent de-dupes by video id, not by date, so both sessions of a day survive. Measured in the store: of 937 distinct docket dates, 584 carry two streams, 83 carry three or more, maximum 4 in a day (2024-09-03, 2024-08-09, 2024-06-17, 2024-02-16, 2024-02-02). Store-vs-disk: 1701 dirs hold a transcript, SELECT COUNT(*) FROM dockets is 1701, and the two id sets are identical (0 on disk without a row, 0 rows without a transcript); all 50 clips.file_path values point at files that exist; 0 orphaned cases, 0 orphaned clips. All 1702 transcripts parse, none is empty, all carry genuine per-word timings (60-file sample: duplicate-timestamp fraction max 0.004, 60/60 monotonic, 0 zero-length gaps in the first 3000 words of a sampled file), median 16,327 words. Counting streams per 5-day window over the last 350 days, 17 windows exceed source.scan_depth 8 (worst: 11 streams in the five days from 2025-12-08).
WHY-IT-MATTERS: The two failure modes the brief suspected — half the days silently dropped, and the store drifting from the disk — are not present, and the word-level timing the shorts pipeline depends on (STATE.md: "Gaps come from the word-level transcript now") exists for the whole corpus. The one live risk is that a busy week plus a short outage can push the backlog past a listing depth of 8 while max_age_days still says 4, and discover() logs only "N new and eligible" without naming what it dropped.
PROPOSAL: Raise source.scan_depth from 8 to 25 so the listing always covers more than the 4-day age window even in the channel's busiest weeks; list_recent uses --flat-playlist (discover.py:115-116) so the extra depth costs one request either way. Additionally log the ids dropped by each gate in filter_new so an aged-out docket leaves a trace.
COST: One config value plus a few log lines. Risk is negligible — filter_new already drops anything terminal, under min_duration_s, or past max_age_days, so a deeper listing adds no processing.

## F11: The next `boyd run` will delete all 45 scored.json analysis caches, because cleanup keeps only *.transcript.json and applies retention.work_days to every work dir indiscriminately
SEVERITY: high
EVIDENCE: pipeline.py:921-936 — `keep_days = self.cfg.get("retention.work_days", 3)`, then for every work dir whose mtime is older than the cutoff it unlinks every file `if f.is_file() and not f.name.endswith(".transcript.json")` and rmtrees every subdirectory. config/pipeline.yaml:595 sets `work_days: 3`. Measured now: 45 scored.json files exist and all 45 sit in dirs whose mtime is older than 3 days (newest is 2026-08-18 15:47:16); 1752 of 1760 work dirs are past the cutoff. cleanup() is called unconditionally from cmd_run (cli.py:137 `pipe.cleanup()`) and from cmd_cleanup (cli.py:444), so the next daily run wipes them. The other two retention keys are dead: `grep -rn "keep_transcripts_days|posted_days|work_days" src scripts` returns exactly one hit, pipeline.py:922, so retention.keep_transcripts_days: 365 and retention.posted_days: 90 are never read by anything.
WHY-IT-MATTERS: scored.json is the analysis cache that analyze_docket short-circuits on (pipeline.py:103-104) and that backfill_analyse.py:53 uses to decide what is already done. Deleting it throws away the LLM spend for 45 dockets and forces a full re-segment and re-score of each on next contact — and because the re-check score is not stable across runs (measured: the same case scored 90.8 then 90.0, and 85.6 then 85.0, in run_2026-08-14.log versus run_2026-08-14b.log), the rebuilt cache is not guaranteed to reproduce the same picks. Combined with F7, a docket left at status='discovered' after a cache hit gets re-analysed from scratch every time.
PROPOSAL: Add scored.json to the keep list alongside *.transcript.json (both are small JSON, not the multi-gigabyte media the retention rule exists for), and wire retention.keep_transcripts_days so the config stops describing behaviour that does not exist.
COST: A one-line predicate change plus reading one more config key; under an hour. Risk: work dirs stop shrinking as much, but scored.json files are kilobytes — the 45 on disk are negligible next to the 4.65 GB of json3 that F8 addresses.
